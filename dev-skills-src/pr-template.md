# PR 본문 템플릿 — 사람이 읽는 글

`implement`가 작업 PR을 열 때 이 구성으로 본문을 쓴다. 읽는 사람은 코드를 열기 전에 이 글로 "무엇이 왜 바뀌었고, 어디까지 확인됐고, 내가 볼 곳이 어디인가"를 알아야 한다. 릴리즈 PR 본문은 `ship`이 따로 쓴다.

## 쓰는 법

- **합쇼체로 쓴다.** 짧은 문장, 한 문장에 한 사실.
- **클래스 이름은 처음 나올 때 역할과 함께 쓴다** — "`PrevueDaemon`(프리뷰를 렌더하는 상주 프로세스)", 그 뒤로는 이름만. 리뷰어가 diff와 맞춰 보는 손잡이다. 함수 · 내부 파일 경로 · 변수 이름은 쓰지 않고 동작과 역할로 쓴다("저장하면 이전 그림이 남아 있던 문제"). 사용자가 보는 이름은 쓴다 — CLI 명령 · 플래그 · 스킬 이름 · 사용자가 여는 설정 파일. 빼면 무엇이 바뀌었는지 설명할 수 없다.
- **리뷰어가 모르는 말은 풀어 쓴다.** 하네스 · 스킬 안의 용어와 코드 안 분기 이름을 그대로 옮기지 않는다. 화면 확인 결과는 확인한 동작과 끝 커밋만 쓴다.
- **bullet 하나에 판단 · 사실 하나다.** 굵은 첫머리에 결론을 먼저 써서 굵은 글씨만 훑어도 요지가 잡히게 한다. 나열이 셋을 넘으면 괄호에 넣지 않고 하위 bullet로 펼친다.
- **구조 변경 다이어그램은 사용자가 요청했을 때만 넣고**, 거기도 컴포넌트(데몬 · 뷰어 · CLI) 단위까지만 쓴다.
- **리뷰 용어를 쓰지 않는다.** 별도 "리뷰" 절도, "머지 위험" 줄도 두지 않는다. 사람이 알아야 할 것은 아래 "꼭 봐 주세요"로 간다.

## 구성 — 이 순서로

각 절은 `##` 제목으로 둔다. "있을 때만"인 절은 해당이 없으면 절째 뺀다.

1. **관련 이슈** (GitHub 이슈가 있을 때만) — `Closes #<번호>` 또는 `Refs #<번호>`. 저장소 밖 키(작업 노트 이름 등)는 쓰지 않는다.
2. **문제 / 동기** — 어떤 상황에서 무엇이 불편했거나 막혔는지. 사용자 입장에서 한두 문단.
3. **설계 판단** — 왜 이 방법을 골랐는지, 버린 대안과 이유. 범위 밖으로 남긴 것은 여기 "이번에 하지 않은 것"으로 적는다.
4. **핵심 수치** — 작업이 줄이거나 늘리려던 수치가 있으면 맨 위에 "목표 수치: <무엇> <전> → <후> (기준 <값>)" 한 줄을 두고, 문제 / 동기에서 되풀이하지 않는다. 그 아래 코드와 테스트 코드를 나눠 변경 파일 수와 줄 수 변화(`+추가 / -삭제`)를 적는다. `git diff --shortstat $(git merge-base origin/develop HEAD) -- <경로>`를 테스트 경로(`tests/` · `src/test` · `src/integrationTest`, `dev-skills-src/review.md`의 `test_dirs`와 같은 것)와 나머지에 따로 돌려 얻는다 — 한 번에 돌리면 합계 한 줄뿐이다.
5. **구조 변경** (사용자가 다이어그램을 요청했을 때만) — As-is → To-be 순서로 그림 둘.
6. **실행 화면** (화면이나 출력이 바뀐 PR일 때만) — 바뀐 출력의 발췌를 붙인다. 이미지는 에이전트가 본문에 올릴 수 없으니 "확인하지 못한 것"에 "스크린샷은 사람이 붙일 것"으로 남긴다.
7. **검증** — 이 PR 본문에서 가장 중요한 절이다. 세 묶음으로 쓴다.

### 검증의 세 묶음

**확인한 것** — 성공 기준마다 한 줄. "어떤 상황에서 무엇을 했더니 어떻게 됐다"를 사람 말로 쓰고, 끝에 수단을 괄호로 붙인다(화면 확인 · 테스트 · 직접 확인). CI 실행 링크도 여기 둔다. 화면 확인이 해당 없었으면 "화면 확인 해당 없음 — <이유>"를 이 묶음에 쓴다.

**확인하지 못한 것** — 리뷰어가 이어서 확인하고 체크할 수 있게 항목마다 `- [ ]` 체크박스에 굵게 무엇을, 이어서 왜 못 했는지를 쓰고, 확인 방법은 그 아래 번호 단계로 쓴다. 없으면 "없음"이라고 쓴다 — 빈칸과 구분되게.

**꼭 봐 주세요** (있을 때만) — 사람 리뷰어가 눈으로 봐야 하는 것만 모은다.

- 리뷰가 diff만으로 확정하지 못한 위험
- 고치지 않은 리뷰 지적과 그 이유
- 리뷰어 추천안으로 처리한 물을 것 — 질문과 고른 것
- 리뷰어를 요청한 등급보다 낮은 effort로 띄웠다면 그 사실(요청 등급과 실제 값)
- 독립 리뷰를 못 했다면 그 사실

## 본문 끝

세션의 PR 서명 줄로 끝낸다.

## 예시 — 골격만

```markdown
## 문제 / 동기
`prevue reload` 직후 같은 카드를 다시 열면 이전 그림이 잠깐 보였습니다. …

## 설계 판단
- **새 그림을 받기 전까지 카드를 비웁니다.** 깜빡임이 늘지만 낡은 그림을 보는 것보다 낫다고 판단했습니다.
- **이번에 하지 않은 것: 여러 기기 카드의 동시 갱신 순서 보장.**

## 핵심 수치
- 코드: 파일 3개, +42 / -17
- 테스트 코드: 파일 2개, +88 / -0

## 검증
**확인한 것**
- 저장소 예제 앱에서 저장 직후 카드를 열었더니 새 그림만 보였습니다 (화면 확인)
- CI 전체 통과 — <실행 링크>

**확인하지 못한 것**
- [ ] **실기기 스크롤 체감** — 화면에서 느끼는 부드러움이라 잴 수 없었습니다.
  1. `--watch`로 띄웁니다.
  2. 카드를 빠르게 넘겨 끊김이 없는지 봅니다.

**꼭 봐 주세요**
- 카드를 비우는 시간이 길어질 수 있습니다. 큰 프리뷰에서 직접 보면 좋겠습니다.
```
