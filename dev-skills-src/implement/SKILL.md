# Implement

작업 하나를 세 상태로 끝낸다. 브랜치 · 워크트리 · 머지 같은 규칙은 `AGENTS.md`에 있다.

| 상태 | 할 수 있는 것 | 나가는 길 |
|---|---|---|
| 만들기 | 아래 도구를 어떤 순서로든, 몇 번이든 | 승인 진입 조건이 전부 참이면 승인으로 |
| 승인 | 보고하고 기다리기만 한다. **코드를 고치지 않는다** | 피드백이 오면 만들기로, 머지되면 정리로 |
| 정리 | 기록, 회고, 워크트리 정리 | 끝 |

리뷰와 화면 확인은 커밋마다 다시 하는 점검이 아니라 필요하다고 볼 때 쓰는 도구다. 하지 않은 것은 기록 파일에 이유와 함께 남기고 승인 보고에 보인다.

사람에게 묻는 곳은 계획을 합의할 때, 리뷰나 화면 확인에서 물을 것이 나왔을 때, 구조를 바꾼 PR에 다이어그램을 넣을지 정할 때, 승인(머지)할 때, 정리에서 워크트리를 지울 때다. 그 밖에는 묻지 않고 진행한다.

아래 경우에는 진행을 멈추고 무엇이 왜 어긋났는지 보고한다.

- 합의한 성공 기준을 맞출 수 없거나, 범위를 바꿔야 할 때
- `review` 스킬이 있는데 리뷰어를 띄울 수 없을 때
- 대상 저장소의 Gradle을 돌려야 할 때(`AGENTS.md` "승인이 필요한 것")
- PR의 CI가 실패했을 때

## 시작

`git fetch`를 한 뒤 위에서부터 보고 처음 맞는 것을 한다. 작업 기준은 `origin/develop`이다. 합의한 계획이 대화에 없으면 작업 인계가 가리킨 곳에서 읽는다.

1. 베이스 체크아웃에서 불렸다 — 아무것도 만들지 않고 멈춘다. 작업 워크트리 안에서 다시 부르라고 알린다.
2. 이 브랜치의 PR이 머지됐다 — 정리로 간다.
3. 이 브랜치의 PR이 머지 없이 닫혔다 — 아무것도 고치지 않고 멈춰 보고한다.
4. 그 밖에는 기록 파일과 끝 커밋으로 승인 진입 조건을 확인하고, 거짓인 것부터 만들기에서 채운다.

## 만들기

**합의 전에는 코드를 고치지 않는다.** 합의한 계획이 없으면 계획 합의하기부터 한다.

### 도구

| 도구 | 언제 | 나오는 것 |
|---|---|---|
| 계획 합의하기 | 합의한 계획이 없거나, 계획으로 되돌아갈 때 | `grilling`으로 정한다(없으면 대화로 같은 칸을 보이고 합의한다). 인계가 인용한 커밋 · 코드 줄 · 관찰값과 문서 문장의 사실 주장은 계획을 보이기 전에 지금 코드에서 확인하고(`git cat-file -e` · `git log -S` · 그 줄 읽기), 어긋난 것은 계획에 적는다. 산출물 형식(아래 "계획의 모양")을 넘기고, `[최종]`이 합의다. 작업 인계나 세션 규칙이 정한 기록이 있으면 여기서 한다 |
| 검증 돌리기 | 코드를 고친 뒤 | `tools/check-local.sh`의 통과 — [tools/verify.md](tools/verify.md) |
| 리뷰 맡기기 | 이 작업에서 아직 리뷰받지 않았을 때, 첫 리뷰 뒤의 수정에 리뷰가 볼 것이 있을 때(맡기지 않는 수정은 [tools/review.md](tools/review.md) "고칠 것") | 고칠 것 · 물을 것 — [tools/review.md](tools/review.md) |
| 화면으로 확인하기 | 사용자에게 보이는 동작(뷰어 화면, CLI 출력)이 바뀌어 직접 봐야 한다고 판단할 때. 확인할 때는 계획에 적혔든 아니든 바뀐 보이는 동작 전부를 본다 | 뷰어 화면 · CLI 출력의 확인 기록 — [tools/screen.md](tools/screen.md). 아래 "화면 확인 결과" |
| PR 올리기 | PR이 없거나 본문이 현재 상태가 아닐 때, CI 결과가 없을 때 | 열린 PR과 초록 CI — [tools/pr.md](tools/pr.md) |

### 계획의 모양

계획은 코드 블록에 넣지 않고 마크다운으로 보인다. 칸마다 굵은 머리말로 시작하는 문단이고, 칸 사이는 빈 줄로 나눈다.

- **무엇을** — 무엇이 문제이고 무엇이 달라지는지, 식별자 없이 평이한 말로.
- **고칠 자리** — 고칠 파일 · 함수 · 변수 이름을 여기에 모은다.
- **성공 기준** — 기준마다 굵은 관찰 한 줄, 그 아래 무엇으로 확인하나.
- **뺀 것** — 뺀 것과 이유.

### 만들 때 지킬 것

계획을 세우는 동안 코드는 읽기만 한다.

1. 합의한 성공 기준을 하나씩 달성한다. 기준마다 무엇을 실행해서 무엇을 확인했는지 기록 파일에 적는다. 코드는 `dev-skills-src/coding.md`를 따른다.
2. 동작을 바꿨으면 테스트를 쓰고, 쓰지 않았으면 이유를 적는다.

### 화면 확인 결과

제품 입력이 develop과 같으면 해당 없음으로 기록한다(판정은 [tools/screen.md](tools/screen.md)).

- **결함**: 커밋한 뒤 고치고 검증 돌리기를 다시 통과시킨다. 수정 확인을 맡길지와 다시 볼지는 고친 것에 따라 정한다(위 도구 표).
- **애매한 것**: 한 번에 모아서 묻는다.
- 확인하지 않았거나 못한 것은 진행을 막지 않고 이유와 함께 PR "확인하지 못한 것"과 승인 보고에 적는다(해당 없음은 제외 — "확인한 것"에 쓴다) — 무엇이 해당하는지는 [tools/screen.md](tools/screen.md).

### 피드백을 받았을 때

**계획으로 되돌아가기.** 리뷰나 사람의 피드백이 합의한 결정이나 참조 구현과 맞지 않으면, 코드를 고치지 말고 계획 합의하기로 돌아간다. `grilling`으로 그 결정을 다시 정하고, 바뀐 계획을 지적된 줄만이 아니라 남은 코드 전체에 적용한다. 같은 PR에서 구조(상태를 어디에 둘지, 레이어 경계, 키, 수명)를 바꾸라는 피드백을 두 번째 받으면 계획이 어긋난 것으로 본다.

**승인에서 돌아왔을 때.** 무엇을 다시 할지(리뷰 · 화면 확인)는 고친 것에 따라 정한다. 검증 돌리기와 PR 갱신은 승인 진입 조건이 요구한다.

이 PR에 새 대상이나 새 파일을 더하는 일은, 이 PR이 머지된 뒤 새 작업으로 시작한다. 사용자가 같은 PR에 얹으라고 하면 그렇게 한다.

## 승인 진입 조건

끝 커밋 기준으로 전부 참이어야 승인으로 간다.

1. 합의한 계획이 있고 성공 기준마다 확인 기록이 있다
2. `sh tools/check-local.sh`가 깨끗한 작업 트리에서 0으로 끝났다
3. PR이 열려 있고 본문이 현재 상태이며 필수 CI가 초록이다
4. 이 작업에서 리뷰를 적어도 한 번 받았고, 받은 리뷰 모두의 고칠 것을 고치고 물을 것에 답을 받았다(`<merge-base>..<끝 커밋>` 범위로 돌린 분류기가 `skip`이면 해당 없음, `review` 스킬이 없으면 "독립 리뷰 없음"을 적었다)
5. 이 작업의 diff(merge-base 기준)에서 한쪽 문(`dev-skills-src/review.md` "한쪽 문 신호")에 닿는 변경을 담은 커밋은 모두 리뷰받았다 — develop 병합 커밋은 충돌을 풀며 고친 줄만 본다
6. 기록 파일에 리뷰와 화면 확인을 받은 커밋 SHA와, 그 뒤 맡기지 않은 커밋과 이유가 적혀 있다

조건과 성공 기준별 확인 기록은 작업 트리의 `agentdocs/implement/<브랜치>.md`에 적는다. 조건마다 확인한 커밋 SHA와 결과를 한 줄로 쓴다. 리뷰와 화면 확인의 기록(조건 6)은 끝 커밋과 달라도 문이 깨진 것이 아니다. 증거 그림은 `.cache/` 아래에 두고 경로만 적는다.

## 승인

머지는 하지 않는다. 아래를 보고한다 — 첫 블록은 "사용자가 볼 것"이다.

1. **사용자가 볼 것** — 조건 6의 기록을 옮긴 것(예: "리뷰 · `a1b2c3d`까지 high로 받음. 그 뒤 주석 제거 한 커밋은 맡기지 않음"), 리뷰가 diff만으로 확정하지 못한 위험, 확신이 낮은 판단, 확인하지 못한 것. 확인하지 못한 것이 있을 때만 이 워크트리 빌드로 띄우는 명령을 붙인다.
2. PR 링크, 끝 커밋, 조건별 결과.

머지는 사람이 한다. 머지 전에 사용자 피드백(코드 리뷰, 직접 찾은 버그)이 오면 만들기로 돌아간다.

## 정리

PR이 머지됐을 때만 한다. 아래 순서로 한다.

1. 작업 트리의 `agentdocs/`에 머지 뒤에도 남겨야 할 파일이 있으면 베이스 체크아웃의 `agentdocs/`로 옮긴다. 워크트리를 지울 때 git이 무시하는 파일도 함께 지워지기 때문이다.
2. 작업 인계나 세션 규칙이 정한 기록이 있으면 여기서 한다. 옮긴 파일 경로도 재료에 넣는다.
3. `retro` 스킬을 남기기로 불러서(없으면 건너뛴다), 이번 작업에서 환경 때문에 헤맨 곳을 기록한다. 묻지 않고 기록만 한다. 규약은 `dev-skills-src/retro.md`다.
4. 바뀐 것, PR 링크, 머지 커밋, 확인 결과, 회고 노트, 남은 수동 확인을 한 번에 보고한다.
5. 착수 인계에 끝내기 절차가 있으면 사용자에게 묻고 그 절차대로 자기 워크트리를 정리한다. 없으면 `plugin/bin/prevue stop --mine`으로 데몬을 멈추고 원격 작업 브랜치를 지운 뒤 "워크트리 정리 남음 — <워크트리 경로>"를 보고한다. 다른 세션의 워크트리는 머지됐어도 건드리지 않는다.
