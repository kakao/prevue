# PR 올리기

검증 돌리기를 통과한 커밋을 밀고 `gh pr create --base develop`으로 연다 — 드래프트로 만들지 않는다. 이미 열린 PR이 있으면 커밋을 올리고 본문만 고친다.

## 본문

`dev-skills-src/pr-template.md`를 복사해 `<…>`를 채운다. 절 순서는 틀 그대로이고, "있을 때만"인 절 · 줄은 해당이 없으면 통째로 뺀다. 자리표시 줄은 남기지 않는다. 읽는 사람은 코드를 열기 전에 이 글로 "무엇이 왜 바뀌었고, 어디까지 확인됐고, 내가 볼 곳이 어디인가"를 알아야 한다. 릴리즈 PR 본문은 `release`가 따로 쓴다.

**문체**

- **합쇼체로 쓴다.** 짧은 문장, 한 문장에 한 사실.
- **클래스 이름은 처음 나올 때 역할과 함께 쓴다** — "`PrevueDaemon`(프리뷰를 렌더하는 상주 프로세스)", 그 뒤로는 이름만. 리뷰어가 diff와 맞춰 보는 손잡이다. 함수 · 내부 파일 경로 · 변수 이름은 쓰지 않고 동작과 역할로 쓴다("저장하면 이전 그림이 남아 있던 문제"). 사용자가 보는 이름은 쓴다 — CLI 명령 · 플래그 · 스킬 이름 · 사용자가 여는 설정 파일. 빼면 무엇이 바뀌었는지 설명할 수 없다.
- **리뷰어가 모르는 말은 풀어 쓴다.** 하네스 · 스킬 안의 용어와 코드 안 분기 이름을 그대로 옮기지 않는다. 화면 확인 결과는 확인한 동작과 확인한 커밋만 쓴다.
- **bullet 하나에 판단 · 사실 하나다.** 굵은 첫머리에 결론을 먼저 써서 굵은 글씨만 훑어도 요지가 잡히게 한다. 나열이 셋을 넘으면 괄호에 넣지 않고 하위 bullet로 펼친다.
- **리뷰 용어를 쓰지 않는다.** 별도 "리뷰" 절도, "머지 위험" 줄도 두지 않는다. 사람이 알아야 할 것은 "꼭 봐 주세요"로 간다.

**절마다**

- **관련 이슈** — `Closes #<번호>` 또는 `Refs #<번호>`. 저장소 밖 키(작업 노트 이름 등)는 쓰지 않는다.
- **설계 판단** — 범위 밖으로 남긴 것은 "이번에 하지 않은 것"으로 적는다.
- **핵심 수치** — 목표 수치 줄은 문제 / 동기에서 되풀이하지 않는다. 파일 · 줄 수는 `git diff --shortstat $(git merge-base origin/develop HEAD) -- <경로>`를 테스트 경로(`tests/` · `src/test` · `src/integrationTest`, `dev-skills-src/review.md`의 `test_dirs`와 같은 것)와 나머지에 따로 돌려 얻는다 — 한 번에 돌리면 합계 한 줄뿐이다.
- **구조 변경** — 컴포넌트(데몬 · 뷰어 · CLI) 단위까지만 그린다. As-is · To-be 그림을 PNG로 내보내 아래 "이미지 붙이기"대로 올린다.
- **실행 화면** — 화면 확인에서 찍은 스크린샷 · PNG 중 바뀐 것이 보이는 것을 골라 아래 "이미지 붙이기"대로 올린다. 텍스트 출력은 발췌로 둔다.
- **이미지 붙이기** — 본문에 `![As-is](./as-is.png)`처럼 본문 파일 기준 상대경로로 적고 같은 파일을 `--attach`로 넘긴다(`gh pr create` · `gh pr edit` 둘 다). `gh`가 올리고 그 참조를 업로드 주소로 바꾼다. 본문을 다시 쓸 때는 이미 올린 주소를 그대로 옮기고, 바뀐 이미지만 다시 붙인다.
- **검증** — 이 본문에서 가장 중요한 절이고, 검증의 원 기록이다.
  - **확인한 것** — 성공 기준마다 한 줄, 사람 말로. 화면 확인 결과와 CI 실행 링크도 여기 둔다.
  - **확인하지 못한 것** — "사람 확인 전"인 것. 리뷰어가 이어서 확인하고 체크할 수 있게 쓴다. 없으면 "없음"이라고 쓴다 — 빈칸과 구분되게.
  - **꼭 봐 주세요** — 사람 리뷰어가 눈으로 봐야 하는 것만 모은다.
    - 리뷰가 diff만으로 확정하지 못한 위험
    - 고치지 않은 리뷰 지적과 그 이유
    - 리뷰어 추천안으로 처리한 물을 것 — 질문과 고른 것
    - 리뷰어를 요청한 등급보다 낮은 effort로 띄웠다면 그 사실(요청 등급과 실제 값)
    - 독립 리뷰를 못 했다면 그 사실("독립 리뷰 없음")

- **사용자에게 보이는 변화면 이 PR에서 `CHANGELOG.md`의 `[Unreleased]`에 적는다** — 쓰는 법과 외부 기여 · 제보 멘션은 `dev-skills-src/release-notes.md` — 외부 PR을 머지할 때도 본다.

- **구조를 바꾼 PR이면 본문을 쓰기 전에 구조 변경 다이어그램을 넣을지 사용자에게 묻는다** — 책임 · 클래스를 옮기거나 나누거나 합친 PR이다. 넣으라고 할 때만 그린다. 그림은 `diagram-design` 스킬로 그린다.
- **PR을 연 뒤 커밋을 올리면** 밀고 나서 본문 전체를 현재 상태로 다시 쓴다 — `gh pr edit --body-file`. 갱신 코멘트를 따로 남기지 않는다.

## develop 따라가기

develop이 앞서 충돌하면 `git merge origin/develop`으로 따라가고 검증 돌리기를 다시 통과시켜 민다 — 리베이스 · 강제 푸시를 하지 않는다. 병합이 제품 입력(화면 확인의 경로)을 바꿨으면 화면 확인을 다시 할지 판단한다 — 이 작업이 바꾼 보이는 동작과 병합이 들여온 변경이 겹치면 다시 본다.

## CI

- **기다린다** — `python3 tools/ci_wait.py <N>`. 충돌 확인 → head의 run 찾기 → run이 끝날 때까지 대기 → 필수 체크(`ci-success`) 판정을 한 번에 하고, 종료 코드로 갈린다. `gh pr checks --watch`로 직접 기다리지 않는다 — `ci-success`가 생기기 전이면 "no required checks reported"로 곧바로 끝난다.
- **0 초록이면** PR 본문의 "확인한 것"에 스크립트가 찍은 CI 링크를 채운다. `gh pr merge`는 부르지 않는다 — 머지는 사람이 한다.
- **2 충돌이면** develop과 충돌해 `pull_request` CI가 아예 뜨지 않은 것이다 — 위 "develop 따라가기"대로 병합 · 검증 · 푸시하고 다시 기다린다. 병합으로 충돌을 풀 수 없으면 멈춰 보고한다.
- **1 실패면** 스크립트가 찍은 실패 job · 스텝 · 오류 앞 로그를 읽는다.
  - **외부 다운로드 일시 실패이고 attempt가 1이면 한 번 다시 돌린다** — 의존성 · 툴체인을 받다가 난 HTTP 429 · 5xx · 연결 타임아웃이다. `gh run rerun <run id>`(전체 — fail-fast가 취소한 job까지 다시 돌아야 한다) 뒤 다시 기다리고, PR 본문 "확인한 것"에 재실행했다고 적는다. attempt가 2 이상이면 다시 돌리지 않는다. 워크플로의 Gradle 스텝은 이미 같은 실패를 한 번 스스로 다시 돌므로(`tools/ci-retry.sh`), 여기까지 온 것은 그 재시도도 실패한 경우다.
  - **그 밖에는 멈춰** 어느 job · 스텝이 무엇으로 실패했는지 요지를 보고한다 — 테스트 · 빌드 자체의 실패는 불안정해 보여도 다시 돌리지 않는다. 다시 불려 고쳤으면 수정 확인을 맡길지 고친 것에 따라 정한다([review.md](review.md) "고칠 것"). 맡기면 분류기에 `--range <실패한 head>..HEAD --recheck`, 직전 결과 자리에 CI 실패 요지를 넘긴다.
- **3 · 4면** 상한 안에 run이 생기지 않았거나(3) `gh`가 실패했다(4) — 찍힌 사유를 보고 한 번 더 부르고, 같으면 멈춰 보고한다.
